I support the deterministic pipeline as IGNIS's work-order foundation, especially keeping report numbers in code and making extraction measurable. I would push back on excluding RAG and graph reasoning entirely because they involve probabilistic steps. We can bound their jobs and test them independently without making them the main decision-maker.

For the demo, I suggest a **bounded implementation first**:

- **Graph:** a small, explicitly reviewed asset -> component -> applicable document/case map. Its job is to select the correct equipment/model/version and exclude unrelated evidence, not infer root causes.
- **RAG:** retrieve at most a few applicable passages from that scope, retaining document/chunk IDs and versions.
- **Model:** use the frozen facts and retrieved context to propose a cited explanation, alternatives, uncertainty and a possible inspection, or abstain. Keep extraction and contextual explanation as separate tasks; an extraction fine-tune does not automatically train diagnostic reasoning.
- **Code and people:** code still owns counts, numeric alerts and triage priority. Experts confirm/correct the explanation and separately authorise maintenance actions. An alert should remain available if retrieval or generation fails.

That gives us context awareness while keeping the first build small: one synthetic pump, a lightweight JSON applicability graph, a small document corpus and top-three retrieval. We do not need a graph database or a multi-agent framework for this slice. We can compare facts-only, retrieval, and graph-filtered retrieval on the same cases; whether context improves the explanation is something to measure, not assume.

I also checked additional data sources. **MaintIE remains appropriate for extraction, but it does not provide the evidence-grounded reasoning examples for this extension.** Candidates worth considering are:

1. **[Industrial-Instruction](https://huggingface.co/datasets/Parssky/industrial-instruction-dataset)** — the strongest new candidate for an evidence-use pilot. The current `pana_qa_v1` release has 12,557 training / 1,000 test questions; `pana_qa_claude_v1` has 25,252 / 1,000. Questions include supporting technical documents and answer choices, with noisy and multi-document retrieval settings. These are synthetic multiple-choice labels, not expert pump diagnoses or citation-ready explanations. We should screen the labels, pin one config, respect the stated CC BY-NC 4.0/source-document terms, and avoid presenting QA gains as proof of diagnostic ability. [Author implementation](https://github.com/parssky/industrial-instruction).
2. **[IBM AssetOpsBench](https://huggingface.co/datasets/ibm-research/AssetOpsBench)** — has compressor, hydraulic-pump and failure-mode/sensor scenarios. I would use it first for maintenance evaluation design. Its expected-response characteristics are not complete gold answer trajectories; any training adaptation needs supporting data and review. Its dataset card states Apache 2.0.
3. **[PANDAX](https://zenodo.org/records/14510798)** — 1,860 question/answer/explanation triples from 20 industrial patents, useful for part-of relationships and technical explanations. The release has mixed model-generated/human-evaluated explanations and differs from operational maintenance; use a reviewed subset and split by patent. Zenodo metadata identifies CC BY 4.0.

For the first demo I would keep the explanation model prompted unless a separate adapter beats that baseline. Build a small original, team-reviewed pump evidence set covering supported explanations, absent/conflicting context, wrong-model documents and abstention. Do not manufacture asset/time links between these public datasets and our synthetic pump.

Suggested build order: make review decisions explicit and outputs safe on failure -> prepare scoped graph/chunks -> add deterministic synthetic hourly assessment with alert-first behavior -> add structured contextual explanation and validation -> expert review/report -> compare alternatives and rehearse failure cases. This extends the PR's foundation toward the agreed IGNIS direction without turning the demo into the entire future platform.
